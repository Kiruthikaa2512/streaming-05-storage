## Custom Project

### Dataset

This custom project uses the original `data/sales.csv` dataset provided with the project. The dataset contains sales order records that represent customer purchases. Each record includes fields such as `order_id`, `datetime`, `region_id`, `currency_code`, `product_id`, `unit_price`, `quantity`, `is_online`, `customer_id`, `payment_method`, `referral_source`, `discount_code`, and `customer_note`.

I used the original sales dataset and did not change the input CSV file. Instead, I customized the consumer logic to add business intelligence after each sales message was consumed from Kafka.

### Kafka Messages

The Kafka producer reads rows from `data/sales.csv` and sends each sales order as a Kafka message. The producer uses the configured Kafka topic `product-sales-case`. The message key is based on the region, such as `US-TX`, `US-CA`, `US-MO`, `CA-QC`, or `CA-ON`.

I did not change the producer message fields. The producer still sends the original sales order data. My custom work happens in the consumer after the message is received.

### Consumer Processing

My custom consumer file is `src/streaming/kafka_consumer_kiruthikaa.py`. The consumer receives sales order messages from Kafka, validates the required fields, enriches each valid message with calculated values, and writes the processed results to output storage.

The consumer calculates `subtotal`, `tax_amount`, and `total`. I extended the consumer to also classify each order into a `revenue_tier` based on the final order total:

* `HIGH_VALUE` for orders with total greater than or equal to 150
* `MEDIUM_VALUE` for orders with total greater than or equal to 75
* `STANDARD_VALUE` for orders below 75

I also added a supply-chain oriented `fulfillment_priority` field:

* `CRITICAL` for high-value orders
* `PRIORITY` for medium-value orders
* `NORMAL` for standard-value orders

The consumer logs these classifications while processing messages and writes the results to `data/output/consumed_sales.csv`. The output CSV now includes both custom fields: `revenue_tier` and `fulfillment_priority`. The project also writes processed records to DuckDB at `data/output/sales.duckdb`.

### Experiments

For Phase 4, I copied the original consumer file and created my own custom consumer named `kafka_consumer_kiruthikaa.py`. My initial technical modification was adding `revenue_tier` classification logic after the existing enrichment step. This allowed the consumer to classify each order as `HIGH_VALUE`, `MEDIUM_VALUE`, or `STANDARD_VALUE`.

For Phase 5, I extended the idea into a supply-chain application by adding `fulfillment_priority`. This connects the sales stream to order-processing decisions. In a fulfillment environment, high-value orders may need more attention, faster handling, or additional review, so the consumer marks them as `CRITICAL`.

### Results

When I ran the producer and my custom consumer, the consumer successfully processed 6 sales messages from the Kafka topic. The output showed the calculated subtotal, tax, total, revenue tier, and fulfillment priority for each accepted message.

One order with a total of 194.82 was classified as `HIGH_VALUE` and assigned a `CRITICAL` fulfillment priority. Lower-value orders were classified as `STANDARD_VALUE` and assigned a `NORMAL` fulfillment priority.

The custom consumer completed successfully and wrote output to:

* `data/output/consumed_sales.csv`
* `data/output/sales.duckdb`

The CSV output confirmed that the new fields `revenue_tier` and `fulfillment_priority` were included in the processed results.

### Interpretation

This Kafka streaming workflow showed how sales messages can move from a CSV file, through a Kafka producer, into a Kafka topic, and then into a consumer for processing and storage. The original example calculated totals and stored records. My custom version added business intelligence by classifying each order by value and fulfillment priority.

Watching the messages move through Kafka helped me understand how streaming systems can support near real-time operational decisions. A business could use this type of stream to identify high-value orders, monitor regional sales activity, prioritize fulfillment work, and store processed results for later analysis.

The main business intelligence gained from the consumed messages was the ability to separate standard orders from high-value orders and assign fulfillment priority. This makes the stream more useful for supply-chain and order-management decisions instead of only storing raw sales transactions.
